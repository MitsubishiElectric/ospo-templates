## 1. 本ガイドラインの趣旨

オープンソースソフトウェア（OSS）とは、ソースコードが公開され、複製、改変、配布が許諾されたソフトウェアです。利用にあたっては、各 OSS によってそれぞれ条件が設定されています。  
既存の OSS を改善するために、OSS の開発元に対してソフトウェアやドキュメントなどを投稿したり、あるいは当社オリジナルの OSS を開発し、一般公開したりすることを「コントリビューション」といいます。  
本ガイドラインでは、OSS のコントリビューションに関する確認事項や留意事項を記載しています。OSS のコントリビューションを行う際には、本ガイドラインの社内手続きに従ってください。  
なお、将来、OSS として公開する前提であったとしても、特定の企業のみに公開されている場合は、参加企業の契約や輸出管理などを検討する必要があるため、本ガイドラインの対象外とします。  
コントリビューションではなく、OSS を当社製品やサービスなどに利用する場合は「OSS 活用ガイドライン」を参照してください。

### 1.1. コントリビューションの利点

OSS にコントリビューションすることにより、様々な利点があり、以下に例示します。

#### 【既存の OSS 開発コミュニティへ投稿するメリット】

- 製品に利用した OSS のバグを OSS の開発元へ報告することで、OSS のバージョンアップ版を製品に採用する際、当社による再修正の手間を省ける
- OSS の技術動向を早期に把握することで、当社製品との連携をより戦略的に検討できる
- 当社製品に必要な機能を提案し、当社製品との連携をしやすくできる
- 継続して OSS に貢献することにより OSS 開発コミュニティ内での当社プレゼンスを上げることで、当社が提案した機能の実装を促進できる
- 顧客に対して、製品に採用している OSS に精通した開発者が当社に在籍していることをアピールすることで、信頼性を高められる
- 社外エンジニアとの技術交流により情報収集したり、ソースコードを深く理解したりすることで、個々のスキルを向上できる

#### 【新規に当社プログラムを OSS として公開するメリット】

- 外部からの知見やリソースの流入により、ユースケース・新規機能・課題の発見と実装サイクルが早まる
- 顧客での利用をきっかけに、サポートや有償サービス、共同開発などの機会が生まれる可能性がある
- 他社製品に組み込まれることができれば、業界インフラとしての地位が確立できる
- ユーザーによるテストやレビューによって不具合や脆弱性の早期発見・対策が進む
- 技術力の発信を通じて認知向上や人材確保につながり、社外とのつながりの形成にも寄与する

### 1.2. コントリビューションの例

コントリビューションの例を紹介します。こちらに記載されていないものでも、OSS を改善するために OSS の開発元へ情報提供する活動は、コントリビューションになります。

- 英語の技術ドキュメントを和訳して投稿する
- 古くなった README や Usage の更新案を投稿する
- バグ修正や新規機能を追加するパッチを送る
- タイプミスや誤字などを指摘する
- ユースケースを投稿する
- 新たに OSS プロジェクトを立ち上げる

## 2. コントリビューションの管理

### 2.1. 投稿部門での管理

職務としてコントリビューションを行う場合、上司（管理職）の承諾を得てください（メール等のメッセージでも可）。
上司は、責任者として、以下を管理してください。

#### （1）誰がどの OSS にコントリビューションしているか

職務として作成したソフトウェアやドキュメントは会社に著作権が帰属します。一方、個人的な活動として作成したものについては、個人に著作権が帰属するため、会社の職務と区別する必要があります。
なお、個人的なコントリビューションに関しては、会社は関知しません。

#### （2）いつ、どのような著作物を投稿したか

仮に、投稿した著作物について、著作権侵害や機密情報の漏洩などの問題が発生した場合、どのような内容のものを投稿したかを確認できるようにしておく必要があります。
GitHub など、システム上、情報を把握できる仕組みになっているのであれば、特別な管理を行う必要はありません。
また、輸出管理上、問題が発生しないように管理する必要があります。

#### （3）海外との時差を考慮する必要はないか

職務としてコントリビューション活動を行う場合、時差のある海外エンジニアとのコミュニケーションの都合などで、通常の勤務時間外で対応せざるを得ない可能性があります。
その場合、勤務時間に含める方法を検討し、必要な場合は人事部門と相談してください。

### 2.2. 事前登録

本項では、以下のケースが対象になります。

#### 【対象】

- 当社が開発したプログラムやドキュメント、コンテンツなどの著作物を投稿する  
  - ただし、バグ修正パッチや誤字修正など、創作性（著作権）が発生しない軽微なコードやテキストの投稿、およびコメントのみの投稿を除く
- 投稿に伴い、契約を締結する

当社がコントリビューションしている対象 OSS の全体を把握できるように、<u>初めて投稿する OSS については、以下の「OSS コントリビューション一覧」に必要事項を登録してください。投稿の都度、登録する必要はありません</u>。内容に変更があった場合、あるいは事務局からの情報更新の依頼があった場合には、登録した情報を更新してください。

#### 【OSS コントリビューション一覧サイト】

通知する項目は以下になります。

1. 名称（OSS 名またはリポジトリ名）
2. 投稿先サイトの URL
3. OSS（またはリポジトリ全体）が提供する機能概要
4. 適用ライセンス（多数のライセンスがある場合はメインとなるライセンスでも可）
5. 契約（CLA/DCO/その他）の有無（有の場合は URL 記載）
6. 最初の投稿日（おおよその予定で可）
7. コントリビューションの目的や背景（選択肢あり）
8. 公知の技術／公知とするための技術（選択肢あり）
9. 暗号機能を含むか（選択肢あり）  
   ※詳細は 3.4 項参照
10. 当社にコミッターの有無（名前、メールアドレス、GitHub 等のアカウント）
11. 協力部門（複数部門が協力して投稿する場合、代表部門が通知することも可。ただし、責任者が投稿者を管理できる場合に限る）
12. 投稿代表者名（連絡窓口）、メールアドレス
13. 責任者名（管理職）、メールアドレス
14. 責任者の承認日
15. 活動状況（選択肢あり）
16. 契約管理部門（締結した場合、契約書の写しを添付）
17. 補足事項（契約に関する留意事項など）
18. 最初の登録日付／更新日付

## 3. 投稿内容の自己チェック

既存の OSS に投稿する場合は 4 項、新規に当社オリジナルの OSS を公開する場合は 5 項も参照してください。  
投稿する際は、投稿内容が他社の知的財産権を侵害していないか、当社の知的財産を不用意に公開することにならないか、輸出管理上の問題はないかといったことを確認する必要があります。  
なお、生成 AI を利用して作成・修正したソースコードを投稿する場合は、出力内容をそのまま使用せず、投稿者自身が内容を十分に確認し、処理の内容や動作を理解したうえで投稿してください。  
生成 AI の出力には、誤りや意図しない実装が含まれる場合があるため、必要に応じてテストや既存の仕様との照合を行ってください。

### 3.1. 著作権

ソースコードやドキュメントなどの著作物を投稿する場合、当社は、その著作物を対象 OSS の利用者に複製や改変、配布することを許諾することになります。  
そのため、当社に許諾する権利（著作権）があることを確認する必要があります。  
特に、お客様や他社との契約に基づき開発したものについては、契約にて当社の著作権を相手方へ譲渡していたり、当社が著作権を保有する場合でも目的外での利用禁止などの制限が課されていたりすることがありますので、契約内容を確認してください。  
また、投稿内容に他の OSS を含む場合は、その OSS のライセンス条件を遵守する必要があります。複数の OSS を利用する場合は、OSS のライセンス条件が両立することも確認してください。  
なお、当社が著作権を保有する場合は、著作権表示を記載することが可能です。  
ただし、OSS の開発元によっては著作権表示に記載する著作者をコミュニティの名称や Contributors 等に統一しており、個々の作成者の記載を推奨していないことがありますので、投稿する対象 OSS の運用ルールをご確認ください。

#### 著作権表示

> &copy; 第 1 発行年（改訂年を追記） 会社名

※「c」の文字が表示できない場合には「Copyright」と表示する。

**記載例（プログラムの場合）**

```text
Copyright 2023, 2025 〇〇〇〇 Corporation
```

### 3.2. 特許権など

投稿内容に新規のアイデアを含む場合は、特許権や意匠権（画面意匠）を出願する必要がないかを検討してください。  
投稿した後は公知となってしまうため、権利化することができなくなります。  
投稿内容に、当社の特徴とする技術が含まれる場合、当社・他社の特許権が実施されていないか調査することを検討してください。  
OSS には、当社より下流のライセンシーに特許のライセンスを付与する義務が生じるものもあります。  
また、一般的に OSS のライセンス条件では開発者に対して一切の責任を負わない条件になっていますが、他社の権利を含む OSS を当社が投稿し、かつ当該投稿が当社の技術特徴を含む場合、権利行使される可能性が高まります。

### 3.3. 機密情報

投稿内容に当社や他社の機密情報を含んでいないことを確認することが大切です。  
特に、他社との契約により開発した場合、守秘義務が課されていることがあります。  
自部門で独自に開発した場合は、上司に公開可能な情報であるかを確認してください。  
他部門の情報を含む場合は、既に公開されている情報を除き、開示元の部門に公開可能な情報であることを確認してください。

### 3.4. 輸出管理

外為法上、該当技術を国内の非居住者や海外に提供しようとする場合、原則として経産大臣の許可が必要です。米国等も同様の規制を行っています。  
その要否を確認するため、提供前に該非判定と取引審査を行います。  

貿易外省令 第 9 条第 2 項第 9 号の「ホ 学会発表用の原稿又は展示会等での配布資料の送付、雑誌への投稿等、当該技術を不特定多数の者が入手又は閲覧可能とすることを目的とする取引」は、OSS のコミュニティに公開を目的にプログラムを提供する等の場合を含め、不特定多数の者に公開することを目的として技術を提供する取引を、許可不要としています。
> 「[輸出管理品目ガイダンス](https://www.cistec.or.jp/publication/guidance.html)＜役務取引＞第 18 版」より

OSS コントリビューションにおいては、OSS コミュニティでの審査もなく投稿内容が公開される場合（GitHub の Pull Request へ投稿等）は「不特定多数の者が制限なく無償で入手可能」なので輸管上の取引にあたりません。  
また、OSS コミュニティでの審査がある場合（メーリングリストで投稿等）は取引にあたりますが、「技術を公知にすることを目的とする取引」であるため許可不要となります。  
つまり、いずれのケースでも、取引審査上の該当事項なしとなり、該非判定も不要です。

米国 EAR でも「公開されたもの」として対象外ですが、非標準暗号は除外されているため、BIS（米国商務省産業安全保障局）と NSA（国家安全保障局）の両方にコードを送付するか URL を通知（URL が変更になったら再通知）する必要があります。  
これらに対しては事前の該非判定と取引審査が必要です。

- BIS: <crypt@bis.doc.gov>
- NSA: <enc@nsa.gov>

#### ＊非標準暗号とは

<u>以下を除くもの</u>を指します。

- 正当に認められた国際標準団体（例えば、IEEE、IETF、ISO、ITU、ETSI、3GPP、TIA 及び GSMA）によって採択又は承認された暗号アルゴリズム又はプロトコル

「OSS コントリビューション一覧」（2.2 項参照）への登録をエビデンスとすることで、輸出管理の手続きは完了となります。  
不明点がある場合は、輸出管理の相談窓口へご相談ください。  
投稿後に、必要な手続きを行っていなかったことが判明した場合、投稿者は速やかに事務局及び輸出管理の相談窓口へ報告し、必要な是正措置（投稿の撤回等）を実施してください。

## 4. 既存 OSS へのコントリビューション

インターネットに公開されている OSS に対してコントリビューションする場合、以下の項目を確認してください。

### 4.1. OSS 開発元の評価

投稿する先の OSS および開発元について、当社が積極的に開発にかかわることが適切であるかを評価することが大切です。  
評価するポイントとしては、以下があります。以下に合致した場合、投稿するかどうかは慎重に判断してください。

#### （1）開発元の活動が活発か

OSS が更新されていない場合、当社が投稿したとしても反映されないことが考えられます。

#### （2）OSS に適用されたライセンス条件で利用可能か

当社のビジネス上、遵守しにくいライセンスが適用されていた場合、投稿内容が対象 OSS に反映されたとしても、当社のビジネスに活用することができなくなります。

#### （3）開発元は複数の企業が参加したコミュニティを形成しているか

開発元が単独の会社であった場合、将来、対象 OSS に適用されたライセンスが変更されることがあります。  
当社が遵守しにくいライセンスに変更された場合、当社のビジネスに活用することができなくなります。

### 4.2. 対象 OSS のコントリビューション方法を確認

投稿先である OSS プロジェクトによっては、コントリビューションの方法が定められていることがあります。  
多くの場合、`CONTRIBUTING.md` などの名前が付けられているので、必ず参照しましょう。  
プロジェクトによって異なりますが、バグ報告や機能提案の手順、プルリクエストの作成方法などが記載されているものが多いです。  
なお、脆弱性等、セキュリティに関する情報については、通常のバグ報告とは別にメールで報告する運用にしていることがありますので、個々の OSS の運用を確認してください。

> **注意：メールアドレスの記載**  
> 　投稿する際にメールアドレスを記載する際は、当社の社員用メールアドレスを記載してください。

### 4.3. 投稿時の留意点と進め方

当社が作成したソースコードを OSS コミュニティに採用してもらうためには、提案内容そのものの品質に加え、OSS コミュニティの開発文化や合意形成の進め方に適合していることが重要です。

提案にあたっては、以下の点を総合的に考慮してください。

1. 提案するソースコードは、当社製品固有の要件に限定されず、広く一般に利用可能な汎用的な内容であること。
2. OSS 開発コミュニティのコーディング規約、設計方針、レビュー手順、テスト手順等のルールや作法に適合し、脆弱性を含まないことを十分に確認済みであること。
3. 変更規模は適切であり、必要に応じて小さな単位に分割して段階的に提案すること。大規模な変更はレビュー負荷を高め、既存の開発方針と衝突するおそれがあるため、慎重に扱うこと。
4. ソースコードは、将来的にコミュニティ側で保守・修正・再実装しやすいよう、読みやすく整理されていること。

また、提案を円滑に進めるため、以下の進め方を推奨します。

5. Patch 投稿や Pull Request をいきなり作成するのではなく、メーリングリストや Slack、GitHub Issue 等で既存の議論や関連 Issue を確認し、解決したい課題や提案の方向性がプロジェクトの意図と整合しているかを事前に確認すること。
6. 規模の大きい機能については、実装前に Issue 等で設計方針、影響範囲、実現方法について議論し、合意形成を図ること。
7. 提案内容については、期待できる効果だけでなく、懸念点や制約を含めたメリット／デメリットを整理して示すこと。
8. 設計議論においては、想定ユースケースの少なくとも一つが動作する working example を提示し、実現可能性を具体的に示すこと。
9. Pull Request は、変更範囲が狭く、関係のない変更を含まず、必要なテストが追加され、テストが通ることを確認したうえで作成すること。

#### 参考：バグ報告のためのパッチ投稿

利用している OSS にバグを発見した場合、OSS 開発コミュニティへバグを報告することが望ましいです。  
ただし、既に他から報告されていることもありますので、重複しないように注意してください。  
また、バグだと思っても、自分のコードに問題があるケースもあるため、OSS のバグであるかを慎重に確認しましょう。  
報告する際は、以下を明記することが大切です。  

- バグの再現手順
- 期待される結果
- 実際の結果
- 動作環境（OS、ライブラリ等のバージョンなど）

必要に応じてスクリーンショットやログを添付し、可能であれば、再現するためのテストコードも提供するとよいです。  
報告の方法としては、プロジェクトで定められたコントリビューションの方法を確認してください。  
GitHub の Issue や専用のバグトラッカーシステム、メーリングリストなどが用意されていたり、報告用のテンプレートが用意されていたりすることがあります。  
報告後に開発者から追加情報を求められた場合は、速やかに対応しましょう。

### 4.4. 契約等の確認

OSS の開発元によっては、投稿者による知的財産権の許諾を明確にするために、[DCO（Developer Certificate of Origin）](https://developercertificate.org/)の提出や CLA（Contributor License Agreement）の締結などを求められることがあります。  

それぞれの取り扱いについて説明します。

#### 4.4.1. DCO の扱い

[DCO](https://developercertificate.org/) は、投稿するプログラムやドキュメントについて、投稿者が著作権など正当な権利を有していることを宣言するためのものです。
DCO の提出については、対象の OSS にコントリビューションすることを上司に許可されている場合は署名してかまいません。

参考（日本語訳）：<https://developercertificate.opensource.jp/>

#### 4.4.2. CLA の扱い

CLA は、投稿するプログラムやドキュメントについて、著作権や特許権などの知的財産権を許諾することを約束するための契約書になります。  
OSS の開発元によっては、企業向けの CCLA（Corporate CLA）と個人向けの ICLA（Individual CLA）の 2 種類を用意していることがあります。

##### （1）CCLA

職務としてプログラム等の著作物を提供する場合、会社の権利を許諾することになるため、CCLA を締結することになります。  
CCLA によっては、当社の権利及び関係会社の特許権を含めて無償許諾することを条件としている場合があります。  
CCLA の署名は会社を代表して行うことになりますので、投稿者が個人で署名することはできません。  
内容に不都合な条件がないかを法務部門に確認し、誰が署名するのが適切なのかを判断します。

##### （2）ICLA

CCLA に加えて、個人向けの ICLA の締結も求められることがあります。  
ICLA に署名して投稿するかどうかは個人の判断になります。  
ただし、会社の業務で作成した成果物、会社のノウハウや特許と関連する技術、会社アカウントでの投稿等、個人判断で署名してはいけない場合もあります。  
署名する場合、CCLA と同様に、ICLA の内容を法務部門に確認し、内容に不都合な条件がないことを確認してください。  


法務部門への確認については、1.3 項の相談窓口へ CLA の書面を送付して相談してください。  
なお、既に締結済みのものについては、2.2 項記載の「OSS コントリビューション一覧」を参照してください。既に締結済みのものについては、再度、法務部門への相談は不要です。

#### 4.4.3. その他の契約

OSS コントリビューションにあたり、上記以外の契約を求められることもあります。  
その場合も上記と同様に、契約条件に不都合な点はないかを法務部門に確認したうえで、誰が署名するのが適切なのかを判断してください。

## 5. 当社オリジナルの OSS 公開

当社が新規に開発したプログラムを OSS として公開する場合、以下を検討したうえで、README（付録 A 参照）にプロジェクトの概要、利用方法、前提条件、注意事項等を記載してください。

### 5.1. 目的の明確化と評価基準の設定

当社プログラムを OSS として公開する目的を明確にすることが大切です。  
また、公開後の評価基準を設定しておき、定期的に評価して OSS 化が成功しているかを確認することが大切です。  
なお、公開後、メンテナンスや PR 活動のように継続的な工数が掛かり得ることを考慮しておく必要があります。  

評価基準としては、例えば、以下のような項目が想定されます。

- **利用状況**：ダウンロード数、導入数、利用の広がり
- **コミュニティの活性度**：Issue 件数、Pull Request 件数、外部からの参加状況
- **開発の継続性**：リリース頻度、保守の継続性
- **品質向上への貢献**：不具合報告、修正反映の状況
- **技術的な発信力**：ドキュメントの整備状況、外部での参照状況
- **事業・組織への波及効果**：認知向上、採用への影響、連携機会

参考として、詳細は「Open Source Guides：オープンソース プロジェクトを立ち上げる」に掲載された[「オープンソース プロジェクト始動のチェックリスト」](https://www.linuxfoundation.org/ja-jp/resources/open-source-guides/starting-an-open-source-project?ct=1787790895677)を参照してください。

### 5.2. 名称の決定

当社オリジナルの OSS に名称を付ける場合、他社の商標と一致あるいは類似しないことを確認する必要があります。  
また、OSS 名称が商品名称にかかわるなど必要な場合は商標出願を行い、当社が商標権を確保、維持することを検討することが大切です。  
商標登録されていない場合でも、他の OSS と同じ名称は避けるようにしてください。

- 簡易検査：[特許情報プラットフォーム](https://www.j-platpat.inpit.go.jp/)（工業所有権・研修館サイト）

### 5.3. ライセンスの決定

当社が著作権を保有する OSS については、自由にライセンス条件を決定することができます。  
この場合、他の OSS との組み合わせや公開する OSS の目的などにより、適切なライセンスを選択することが大切です。  
当社の OSS 戦略としては、[OSI 認証ライセンス（日本語参考訳）](https://opensource.org/licenses)のうち、他者が利用する際に障壁の低いライセンスを推奨します。  
ライセンスの決定に困難が生じた際は、事務局へ相談してください。  
なお、既存の OSS を何らかの理由でフォーク（派生）して公開する場合は、フォーク元のライセンスに準じてください。  
ライセンスが決定したら、ルートディレクトリ下にひとつのファイルとしてライセンス文全体を含めてください。  
また、公開するソースコードのコメント行に以下のような [SPDX の Identifier](https://spdx.org/licenses/) を付けることを推奨します。

```text
SPDX-License-Identifier: Apache-2.0
```

> **注意：公開後のライセンス変更**  
> 一旦、公開した OSS のライセンスは、やむを得ない事情がある場合を除き、変更してはいけません。  
> 仮に、社外から投稿された著作物が含まれている場合、その開発者は著作権者の一人になるため、開発者全員の許諾を得ない限り、ライセンスを変更することはできません。  
> 各開発者から許諾を得られた場合でも、新バージョンから変更することとし、変更したことを README や対象 OSS の Web サイトに掲載するなどして周知してください。

### 5.4. 公開後の透明性の確保

当社 OSS を公開し、社外との共創活動を推進するのであれば、その後の仕様検討や議論内容についても公開することをお勧めします。  
例えば、当社で公開する OSS のソースコードを GitHub 上で管理する場合、すべての Issue および Pull Request は、公開の場で行うようにしましょう。  
ただし、機密情報を漏洩しないように注意してください。

### 5.5. 外部からのコントリビューションの対応

OSS を公開する場合、外部からのコントリビューションを受けない選択もありますが、可能な限り、社外の開発者と共創活動を行うことを推奨します。

#### 5.5.1. `CONTRIBUTING.md` の作成

コントリビューションのルールを明確にするために `CONTRIBUTING.md`（付録 B 参照）を作成しましょう。  
GitHub 上で OSS を公開する場合は、Issue 上もしくは Pull Request 上でやり取りしてください。  
ただし、セキュリティに関わるバグ報告に関しては、個別にメール等、公開されない方法で報告してもらいます。

##### 脆弱性の対応

当社の OSS で脆弱性が発見されたとき、また報告を受けたときには、可能な限り速やかに脆弱性を修正したバージョンを公開してください。  
その際は、修正前のバージョンと区別できるバージョン名を付ける必要があります。

#### 5.5.2. CLA/DCO の準備

外部からのコントリビューションに対して知的財産権の扱いを明確にするために、投稿者に対して CLA（CCLA や ICLA）の締結を求めるのか、それとも DCO を求めるのかを事前に検討しておく必要があります。  
どちらを採用するかは、関連する技術分野の OSS の運用例を参考にし、当社 OSS の特性、公開範囲、特許関係への影響等を考慮して判断します。  
CLA を作成して締結を求める場合は、その内容について不都合がないことを事前に法務部門へ確認してください。  
特に CLA の締結を求める必要がない場合、または軽微な変更・バグ修正の受入れ等で十分なのであれば、DCO の提出を求める運用を推奨します。  
CLA や DCO については 4.4 項を参照してください。
